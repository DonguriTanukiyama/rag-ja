# rag-ja — 日本語の社内文書に、出典つきで答えさせる

手元の Markdown / テキストを読み込み、質問に対して**根拠になった文書と行番号を添えて**答える。
モデルもデータもローカルで完結し、外部にテキストを送らない。

```
python rag_ja.py index ./docs        # 文書を読んで索引を作る
python rag_ja.py ask "有給の申請は何日前まで？"
python rag_ja.py eval questions.json # 検索の当たり具合を測る
```

依存は `chromadb` と `requests` の 2 つ。埋め込みと生成は [Ollama](https://ollama.com) に任せる。

---

## なぜ作ったか

社内文書を LLM に読ませる仕組みは、たいてい次のどちらかで失敗する。

1. **もっともらしい嘘を返す。** 資料に書いていないことを、書いてあるかのように答える。
2. **日本語で検索できていない。** 英語圏で作られた埋め込みモデルをそのまま使うと、
   日本語の質問がほとんど区別できない。しかも**それが起きていても画面上は正常に見える。**

この 2 つを、設計で潰すことを目的にした。

---

## 設計

### 1. 出典の無い文を出さない

検索でヒットした断片だけをモデルに渡し、次の制約をかける。

- 資料に書かれていないことは書かない
- 分からない場合は「資料に記載がありません」とだけ答える
- 各文の末尾に、根拠にした資料の番号を付ける

回答の下には、番号と `ファイル名:行番号` と本文の冒頭を必ず並べる。
**読む人が、答えを信じずに原典へ飛べる形にしてある。**

### 2. 埋め込みを差し替えられる。そして、どちらを使ったかを隠さない

起動のたびに Ollama へ問い合わせ、`bge-m3` → `mxbai-embed-large` → `nomic-embed-text` の順に探す。
どれも無ければ Chroma の既定（`all-MiniLM-L6-v2`）に落ちるが、**そのときは警告を出す。**

```
埋め込み: chroma-default / all-MiniLM-L6-v2
  注意: 日本語の検索精度は期待できない。`ollama pull bge-m3` で差し替えられる
```

黙って質の低いほうに落ちるのが、いちばん危ない壊れ方だと考えている。

### 3. 測れる

質問と、その答えが載っている文書の対を JSON で渡すと、
**上位 k 件に正解が入った割合（Recall@k）** と **1 位が正解だった割合** を出す。

```json
[
  {"q": "有給休暇は何日前までに申請するのか", "file": "就業規則.md"},
  {"q": "ラインが止まったとき、最初に誰へ連絡するか", "file": "設備異常時対応手順.md"}
]
```

これがあると、埋め込みを替えたときに**良くなったのか悪くなったのかが数字で分かる。**

## 測定

日本語の Markdown 312 ファイル（3,183 断片）を索引にし、
**答えが載っている文書を人間があらかじめ決めた質問 12 件**で測った。

質問は「〜については、どう決めたか」のような自然な言い回しで、
**正解の文書に出てくる語をそのまま含んでいるとは限らない。**

| 埋め込みモデル | 1位が正解 | Recall@5 |
|---|---|---|
| all-MiniLM-L6-v2（Chroma 既定・英語向け） | **0 / 12 (0%)** | 1 / 12 (8%) |
| **bge-m3（多言語）** | **9 / 12 (75%)** | **12 / 12 (100%)** |

**コードは 1 行も変えていない。埋め込みを差し替えただけ。**

既定のモデルでは、12 問中 9 問で同じ 1 つのファイルが 1 位になった。
日本語の質問を区別できていない。
**それでも検索結果は返ってくるし、生成された答えは日本語として自然に読める。**
測る仕組みが無ければ、この状態のまま運用していたはずだ。

再現手順:

```bash
ollama pull bge-m3
python rag_ja.py index <文書のディレクトリ>
python rag_ja.py eval <質問セット.json>
```

測定に使った文書と質問は私物なので同梱していない。
書き方は `eval.example.json` に置いた。**自分の文書で同じ数字を出せる形にしてある。**

### 分からないときは、分からないと言う

答えの載っていない質問（索引に入っていない話題）を投げると、こう返る。

```
資料に記載がありません [1]

--- 根拠 ---
[1] （関係のない断片）
[2] （別の文書）:28   …連絡可能時間：毎日 5:0…
[3] （別の文書）:266  …週20〜30時間（平日1日あたり4〜6時間程度…
```

**[2] と [3] には「時間」の話が書いてある。** それでも使わなかった。
似た語が拾えたことと、質問に答えられることは別だと切り分けている。

同じことは `-k` を絞ったときにも起きる。上位 3 件に根拠が入らなければ答えを作らない。
`-k` を 8 に増やすと同じ質問に答えられるようになる。
**答えの質は、モデルより先に「何件見せるか」で決まる。**

## 実装のはなし

### 文書の分け方

日本語は空白で単語が切れないので、文字数で数えて 600 字ずつに切り、120 字を重ねる。
切る位置は **空行 → 句点** の順に探し、どちらも見つからないときだけ位置で切る。
機械で作った表やログのように句点の無い文書でも止まらない。

切った断片には、元の文書のどこから来たかを持たせてある。行番号はここから出る。

自己確認（`--demo`）で押さえているのは次の 4 つ。

- ふつうの文書は、すべての断片が句点で終わる
- 句点がまったく無い 2,000 字でも、**文字を 1 つも落とさずに** 4 断片に分かれる
- 空文字・空白のみ・1 断片に収まる短文で落ちない
- CRLF を潰している

3 番目は、実際にバグを 1 件見つけた。
末尾に達しても重なりの分だけ戻ってしまい、**最後の断片が何度も重複して索引に入っていた。**
すべての文書で起きていた欠陥で、動かしている限りは気づけない種類のものだった。

### 速度（RTX 3080 / 10GB）

| 処理 | 実測 |
|---|---|
| 索引 3,183 断片（bge-m3） | 約 4 分 |
| 検索 1 件 | 1 秒未満 |
| 回答（検索＋生成・qwen2.5:7b 既定） | 初回 10.0秒 → 5.4秒 → **0.7秒**（モデルが載るまで） |

生成モデルの既定を 12B ではなく 7B にしてあるのは、**VRAM に両方載せるため。**

埋め込み（bge-m3・1.2GB）と生成モデルは交互に呼ばれる。
gemma3:12b（8.1GB）と足すと 10GB を超え、呼ぶたびに載せ替えか CPU 退避が起きて、
**同じ質問が 600 秒たっても返ってこなくなる。実際にそうなった。**
7B（4.7GB）なら同居できる。`--model` で変えられる。

## 現場の帳票を読む（`genba_norm.py`）

工場の点検表（Excel）や日報は、そのままでは `rag_ja.py` に食わせられない。
`genba_norm.py` は、それを Markdown に直す前処理層。**本体とは独立していて、Markdown を吐くだけ。**

```
python samples/make_samples.py                        # 汚れたサンプルを作る
python genba_norm.py --demo                           # 自己確認＋読み取りの突き合わせ
python genba_norm.py samples/raw -o samples/_norm     # 正規化（1点検 = 1文書）
python rag_ja.py index samples/_norm
python rag_ja.py ask "点検されていない項目は何件ですか" --where doc_type=summary
```

### 中心にあるのは「空欄を消さないこと」

点検欄が空なのは、**異常が無かったから**とは限らない。**そもそも点検していない**ことがある。
表を素朴に読むと空欄は消え、残った「異常なし」だけが文章になる。
その結果、**点検漏れが「異常なし」として索引に入る。**

そこで点検欄を 6 つに分け、**空欄もその理由ごとに全部書き出す。**

| 分類 | 判定するもの | なぜ分けるか |
|---|---|---|
| 記入あり | 異常なし / OK / レ / ✓ / ○ | |
| 異常 | 異常あり… / NG / 不良 | |
| **条件付き許容** | 要観察 / 経過観察 / 軽微 / 稼働可 | **異常ではない**。ここを異常に入れると件数が実態より膨らむ |
| **対象外** | 計画停止 / 停止中 / 休転 | **空欄でも未記入ではない**。設備が止まっていれば点検しない |
| **未記入** | 空欄 | **黙って消さない**。ここが本体 |
| **判別不能** | `-` / `／` / `N/A` | 「該当なし」か「未チェック」か、原票からは決められない |

出力には、**その状態が何を意味しないのかまで書く。**

```
- 活性汚泥槽 色: **判別不能**（原文: -）— 「該当なし」か「未チェック」か決められない。**異常という意味ではない**
- 加圧浮上槽 異音: **対象外** — 計画停止中（設備が稼働していないため点検しない。未記入ではない）
```

**この 1 行で足りた**。生成側のプロンプトは 1 文字も変えていない。
「判別不能を異常と数えてしまうのでは」という指摘を受けて測ったが、**起きなかった。**

### 抽出の網羅率（LLM にも埋め込みにも依存しない）

| | 素朴 | 正規化後 |
|---|---|---|
| 日付が確定した行 | 12 / 25（48%） | **25 / 25（100%）** |
| 点検欄として出てきたマス | 89 / 100 | **100 / 100** |
| 部署の表記 | 4 通り | **1 通り** |

日付の差 13 行は**結合セル**（1 日に 3 回点検した日は、先頭行にしか日付が無い）。
マスの差 11 は**すべて空欄。**

内訳は 記入あり 57 / 異常 11 / 条件付き許容 8 / 対象外 6 / **未記入 11** / **判別不能 7**。
→ **18 マスぶん、点検された記録が無い。**

### 検索を絞れるようにした（`--where`）

文書の先頭に front-matter を置くと、`rag_ja.py` がそれを metadata として索引に入れる。
`--where date=2026-09-03` のように書くと、その条件の文書だけを検索する。

**RAG は検索であって集計ではない。**
「未記入は何件か」に答えさせたいなら、**その一文がコーパスに無ければならない。**
だから正規化と同時に集計文書を 1 本出し、集計を聞くときはそれだけを見せる。

| 質問（qwen2.5:7b・温度 0） | 答え | 正解 | |
|---|---|---|---|
| 記入されていない項目は何件 | 11 件 | 11 | ○ |
| 9 月の異常は何件 | 11 件 | 11 | ○ |
| 点検されていない項目は何件（停止分を除く） | **2 件** | 18 | ✕ |
| 同じ質問に `--where doc_type=summary` | **18 件。ただし停止分は含めていません** | 18 | ○ |

**モデルもコーパスも質問も同じで、違うのはフィルタの有無だけ。**
上位 5 件に個票が混ざると、そこに書かれた個別の「未記入」を数えて小さい数を出す。
**絞らずに 4 問中 3 問、絞って 4 問中 4 問。**

参考までに、素朴なコーパスは 1 問目に「3 件」と自信をもって誤答した（根拠は全部日報）。

### xlsx は標準ライブラリでも読めるが、弱いことは隠さない

xlsx は zip と XML なので依存なしで読める。しかし方言に弱い
（1904 年日付システム / Strict ネームスペース / 旧 `.xls` / 複数シート）。

**openpyxl があれば使い、無ければ内蔵に落ちる。どちらを使ったかは必ず表示する。**
埋め込みの選択と同じ方針で、黙って弱いほうに落ちない。

そのうえで `--demo` が両者を突き合わせる。

```
突き合わせ: 内蔵 == openpyxl 3.1.5（結合14箇所・全マス一致）
```

### データは自作

**実物の点検記録は前職の社外秘で使えない。**
`samples/make_samples.py` は「実物がどう汚れているか」だけを写したサンプルを作る。
1 つの日付列に 6 通りの書式とシリアル値、日付セルの縦結合、2 段ヘッダ、表記ゆれ、
数値に混ざる単位と全角、点検欄の 6 状態。

### 落とした誤り 3 件

| | 内容 | 見つけた経路 |
|---|---|---|
| ① | **「異常なし」が「異常」で始まる**ため接頭辞判定に先に当たり、正常が全部異常に化けていた | `--demo` |
| ② | 別名の置換が正しい形にも当たり、「加圧浮上槽」が「**加圧加圧浮上槽槽**」になっていた | 出力の目視 |
| ③ | **「要観察」を異常に、「計画停止中」を未記入に**数えていた | 外部レビュー |

①②は `--demo` に回帰を入れた。③の教訓は「**現場の状態は 4 つでは足りない**」。

### この層の限界

- **自作サンプル 1 セット・質問 4 問の PoC。実物の帳票では試していない**
- `parse_date` は 1904 年日付システム未対応。`12.3.4` を 2012-03-04 と読む誤検知がある
- 内蔵リーダーは 1 シート目決め打ち。複数シート未対応
- 別名辞書と点検欄の見出しは手書き。**現場ごとに違うので、そのままでは他所に使えない**
- 質問から `--where` を組み立てる仕組みは無い。**今は人間が付けるか決めている**
- 記入率を出すだけで、しきい値もアラートも無い

測定の詳細は [`MEASURE_GENBA.md`](MEASURE_GENBA.md)。
